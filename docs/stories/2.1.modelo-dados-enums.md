# Story 2.1: Modelo de dados nuclear e enums por escrito

## Status
Approved

## Story
**Como** equipa técnica,
**quero** o modelo de dados do domínio GM definido por escrito (enums/FKs aprovados) e migrado,
**para** que todo o resto do épico assente em fundações estáveis, sem repetir a lição da auditoria de 05/07 (`novo≠new`, FK ausente).

## Acceptance Criteria
1. Documento de enums/FKs **aprovado ANTES de correr as migrações** deste épico. A [Arquitectura §2.1](../architecture/ARCHITECTURE-SIC-GLOBAL-MINDS.md) JÁ define os valores exactos (`pipeline_fase` 8 fases, `programa_tipo`, `lead_temperature`, `score_confidence`, `factura_estado`, `financeiro_estado`, `documento_estado`, `conversa_status`, `pause_reason`, `lead_origem`, `consentimento_tipo`, `idioma`) — esta story **valida e regista a aprovação formal do gate, não redesenha**. Estilo fechado: CHECK constraints com valores texto `snake_case` minúsculas sem acento (NÃO `CREATE TYPE ... AS ENUM`).
2. Campo `currency` em todas as tabelas monetárias é **`CHAR(3)` livre validado por regex ISO 4217** (`CHECK (currency ~ '^[A-Z]{3}$')`) — NUNCA enum (o cliente usa EUR, USD, GBP, ZAR, AED, CAD, AUD e moedas futuras não podem bloquear).
3. Migração **008 `008_catalogo.sql`** cria `parceiros`, `destinos`, `programas` com as colunas exactas da §2.5 (incl. `comissao_percent NUMERIC(5,2)` no parceiro + override no programa, `custo_min`/`custo_max NUMERIC(12,2)`, `custo_vida_currency`/`currency CHAR(3)` com regex) e índices `idx_destinos_parceiro`, `idx_destinos_pais`, `idx_programas_destino`, `idx_programas_tipo`.
4. Migração **009 `009_ficha_candidatura.sql`** cria `fichas_estudante` (com `lead_id UUID NOT NULL UNIQUE → leads(id)`, `processo_em_curso BOOLEAN NOT NULL DEFAULT false`, `documentos JSONB DEFAULT '[]'`) e `candidaturas` (com `fase` CHECK das 8 fases, `fase_desde TIMESTAMPTZ`, `prazo_fase_dias INTEGER`) e índices `idx_fichas_lead`, `idx_fichas_processo` (parcial `WHERE processo_em_curso = true`), `idx_candidaturas_lead`, `idx_candidaturas_fase`.
5. Migração **010 `010_leads_qualificacao.sql`** estende `leads` com as colunas da §2.4: BANT (`bant_budget/authority/need/timeline`), `sales_score` (CHECK 0–100), `score_confidence` (default 'low'), `fit_score`, `temperature`, `destino`, `nivel`, `orcamento`, `idioma_pref`, `pipeline_fase` (default 'lead'), `sales_rep_id`, `pipeline_stage_id`, `followup_count`, `tags TEXT[]`, UTM (`utm_source/medium/campaign`) + índices (`idx_leads_fase`, `idx_leads_temperature` parcial, `idx_leads_score DESC`, `idx_leads_followup`) + trigger de cálculo de temperatura (`quente ≥70`, `morno 40–69`, `frio <40`; NUNCA `quente` com `score_confidence='low'`).
6. RLS por papel em todas as tabelas criadas/alteradas nesta story (padrão §8.1: leitura `authenticated`, `DELETE` só admin via `team_members`, `service_role` total); rollback SQL no rodapé de cada migração (`-- ROLLBACK:`).
7. Tabelas herdadas do E1 verificadas como compatíveis: `mudancas_estagio` regista valores de `pipeline_fase` (§2.3) e `consentimentos` usa `lead_id` — o PRD lista-as no AC2 desta story mas a arquitectura cria-as no clone (migrações 002/007, E1); aqui apenas se valida a compatibilidade, sem recriar.

## Dev Notes
- **Fonte vinculativa:** [Arquitectura §2](../architecture/ARCHITECTURE-SIC-GLOBAL-MINDS.md) (2.1 enums, 2.4 extensão `leads`, 2.5 tabelas novas) + §3 (migrações 008–010) + §8.1 (padrão RLS por papel). O documento de arquitectura declara-se explicitamente "o gate técnico da story 2.1".
- **Dependência:** Épico 1 completo — migração 002 (rename `clientes→leads` já feito; nenhuma tabela nova nasce com `cliente_id`), 003 (`team_members`, necessária às policies admin), 007 (`consentimentos`).
- **Esta story é o gate do épico:** 2.2–2.7 só arrancam depois das migrações 008–010 aplicadas.
- **NÃO incluir aqui:** migração 011 (financeiro — story 2.6), 013 (views RFV — story 2.7), 016 (seed catálogo — story 2.2), 015 (seed do agente — Épico 3), 012 (`anonimizar_lead()` — pertence ao fluxo de compliance, story 4.4, apesar de §10.1 mapear o intervalo 008–013 ao E2).
- **Nota `pipeline_stage_id`:** fica criada mas **nula** — a decisão da §2.4 é adaptar o trigger do módulo marketing para observar `pipeline_fase` (feito na story 5.1, migração M_mkt_001). Não criar tabela `pipeline_stages`.
- **Desvio PRD↔Arquitectura registado:** o AC2 do PRD inclui `mudancas_estagio` e `consentimentos` na lista de tabelas a criar; a arquitectura herda-as do clone (E1). Resolvido como AC7 (validação, não criação).

### Testing
- Verificação RLS: `SELECT tablename FROM pg_tables WHERE schemaname='public' AND tablename IN ('parceiros','destinos','programas','fichas_estudante','candidaturas') AND tablename NOT IN (SELECT tablename FROM pg_policies)` → vazio.
- Constraints: `INSERT INTO programas (..., currency) VALUES (..., 'eu1')` → falha (regex); `INSERT INTO candidaturas (..., fase) VALUES (..., 'novo')` → falha (CHECK 8 fases); `UPDATE leads SET sales_score = 101` → falha.
- Trigger de temperatura: `UPDATE leads SET sales_score=85, score_confidence='low'` → `temperature <> 'quente'`; com `score_confidence='high'` → `temperature='quente'`.
- Índices: `SELECT indexname FROM pg_indexes WHERE tablename IN ('destinos','programas','fichas_estudante','candidaturas','leads')` inclui os 8+4 índices da §2.4/2.5.
- Rollback testado em staging: aplicar → rollback → reaplicar sem erro (008, 009, 010).
