# Story 2.3: Pipeline kanban de candidaturas (8 fases)

## Status
Approved

## Story
**Como** Rinaldo,
**quero** ver todas as candidaturas num kanban com as minhas 8 fases reais, com arrastar-e-soltar e sinalização de atrasos,
**para** saber onde está cada estudante sem perguntar à Ana nem abrir Excel.

## Acceptance Criteria
1. Kanban em `app/(app)/kanban/` com as 8 fases reais do enum `pipeline_fase` (Arquitectura §2.1): `lead` → `qualificado` → `consulta_agendada` → `proposta_enviada` → `formalizacao_pagamento` → `candidatura_submetida` → `em_curso` → `concluido`; nomes das colunas exibidos em pt-AO legível.
2. Arrastar-e-soltar persiste `candidaturas.fase` e reinicia `fase_desde = now()`; alterações de outros utilizadores aparecem sem refresh (Supabase Realtime na tabela `candidaturas`).
3. Tempo em fase visível em cada cartão (a partir de `fase_desde`); candidaturas paradas além de `prazo_fase_dias` (prazos da Ficha C2) ficam sinalizadas visualmente (`now() - fase_desde > prazo_fase_dias`).
4. Cada mudança de fase insere registo em `mudancas_estagio` (herdada, com `lead_id` + `estagio_anterior`/`estagio_novo` = valores de `pipeline_fase`) — timeline auditável consumida pela ficha 360º (story 2.4).
5. Cartão do kanban mostra o essencial para decisão: nome do lead, programa/destino (via `programa_id`→catálogo), `temperature` quando existe, tempo em fase; clique abre a ficha do lead.
6. Escrita de fase respeita a RLS por papel; transições servidas pelo índice `idx_candidaturas_fase`.

## Tasks / Subtasks
- [ ] Construir a vista kanban com 8 colunas fixas do enum (AC: 1)
  - [ ] Mapa enum→rótulo pt-AO num único ficheiro (`lib/`), sem strings soltas
- [ ] Drag-and-drop com persistência + Realtime (AC: 2)
  - [ ] `UPDATE candidaturas SET fase=..., fase_desde=now()` numa operação
  - [ ] Subscrição Realtime a `candidaturas` (INSERT/UPDATE) para sincronizar colunas
- [ ] Registo em `mudancas_estagio` a cada transição (AC: 4)
  - [ ] Preferir trigger `AFTER UPDATE OF fase ON candidaturas` (garante auditoria mesmo em escritas fora da UI, ex.: agente E3 move o lead) em vez de insert só no frontend
- [ ] Tempo em fase + sinalização de atraso (AC: 3, 5)
  - [ ] Cálculo relativo a `fase_desde`; badge de atraso quando excede `prazo_fase_dias`
  - [ ] Carregar `prazo_fase_dias` por defeito a partir dos prazos da Ficha C2 (editável por candidatura)
- [ ] Cartão com dados essenciais + navegação para a ficha (AC: 5)
- [ ] Verificação RLS e índice (AC: 6)

## Dev Notes
- **Fonte vinculativa:** [Arquitectura §2.5](../architecture/ARCHITECTURE-SIC-GLOBAL-MINDS.md) (tabela `candidaturas`: `fase`, `fase_desde`, `prazo_fase_dias`, índices), §2.1 (enum `pipeline_fase`), §2.3 (`mudancas_estagio` herdada reutilizada para fases de candidatura). PRD FR10 + §3 (ecrã nuclear nº2, paradigma central).
- **Dependência:** story 2.1 (migração 009 cria `candidaturas`; 002/E1 traz `mudancas_estagio`). O catálogo (2.2) enriquece o cartão mas não bloqueia — cartões sem `programa_id` mostram só o lead.
- **Nota `leads.pipeline_fase` vs `candidaturas.fase`:** ambos existem no modelo (§2.4 e §2.5). O kanban do E2 opera sobre **candidaturas**; o campo do lead serve a qualificação do agente (E3) e o overlay por fase do prompt. Manter coerência quando a candidatura avança (o mesmo trigger pode espelhar a fase no lead) — decisão de implementação a documentar no código; PRD/arquitectura não fixam o espelhamento (desvio menor registado).
- **Consumidores a jusante:** mudança de fase dispara ponto de situação proactivo (story 4.2) e trigger de automação do módulo marketing adaptado para `pipeline_fase` (story 5.1) — nesta story não se cria nenhum destes efeitos, só a auditoria em `mudancas_estagio`.
- **Prazos da Ficha C2:** dependência de conteúdo (documento do cliente já em posse da equipa); se algum prazo por fase não estiver definido, `prazo_fase_dias` fica NULL e a candidatura não é sinalizada (sem valores inventados).

### Testing
- SQL: `UPDATE candidaturas SET fase='qualificado' WHERE id=...` → nova linha em `mudancas_estagio` com anterior/novo correctos; `fase_desde` actualizado.
- SQL: `INSERT INTO candidaturas (..., fase) VALUES (..., 'em_espera')` → falha (CHECK).
- node:test do helper de atraso (`isAtrasada(fase_desde, prazo_fase_dias)`) incluindo NULL → nunca sinaliza.
- Smoke UI: arrastar cartão entre colunas → persiste após reload; segunda sessão de browser vê a mudança via Realtime; cartão além do prazo mostra badge.
