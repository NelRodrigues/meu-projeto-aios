# Story 1.3: Subdomínio, security headers e observabilidade mínima

## Status
Done (construível) — 6 headers no deploy, log.ts com redacção, guia DNS; AC1 (subdomínio) = gate DNS do cliente, provisório .vercel.app activo

## Story
**Como** Global Minds,
**quero** o sistema alojado no meu subdomínio com cabeçalhos de segurança e logs estruturados,
**para** que o SIC seja meu (decisão da acta), seguro e diagnosticável.

## Acceptance Criteria
1. Subdomínio da GM (ex.: `sic.globalmindsconsultoria.com`) aponta para o deploy Vercel com SSL válido. ⚠️ **DEPENDÊNCIA EXTERNA (pendência 3 do brief):** criação do subdomínio + acesso DNS é acção da Global Minds — se não chegar a tempo, o AC é substituído por domínio `.vercel.app` provisório e a story fica `Blocked` apenas neste AC.
2. `vercel.json` com security headers (padrão SIC-MD): CSP, HSTS (`max-age=63072000; includeSubDomains; preload`), `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy`.
3. Logs estruturados JSON em todas as edge functions existentes (`{fn, step, leadId?, ...}`) com **redacção de segredos** (replacer que mascara `token`/`key`/`authorization` — padrão receiver ISILDA).
4. CSP verificada contra as origens reais necessárias (Supabase, Vercel, uazapi, api.anthropic.com, api.resend.com, graph.facebook.com) — sem `unsafe-*` desnecessários e sem bloquear funcionalidades.
5. Documento curto `docs/guides/dns-subdominio.md` com as instruções exactas (registos CNAME) para enviar ao cliente — cumpre a acção B da acta ("enviar instruções de criação do subdomínio").
